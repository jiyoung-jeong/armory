표의 실행 중 action 부족은 **매 에피소드에서 첫 모델 action을 실행한 이후, 사용할 모델 action이 없었던 step의 비율**이다. 첫 응답 수신 시점 기준이 아니다. SD는 세 실행 사이의 표본 표준편차다. chunk 지연 p95는 각 실행의 p95를 구한 뒤 평균한 값이며, 모든 chunk를 합친 p95는 아니다. 실제 배치 평균도 실행별 평균의 산술평균이다.

실험 조건은 pi05_libero/JAX, generation steps=10, lookahead-actions, alpha=1, 20Hz, Hmin=1/Hmax=10, 실험 seed=7, 에피소드 최대 500 step으로 고정했다. 서버 seed와 실험 seed는 7이며 로봇별 시뮬레이션 seed는 7+robot_idx다. 서버는 매번 새로 시작하고 준비 완료 후 180초 rollout을 시작했다. 성공 작업/분의 분모는 전체 로봇을 합친 작업 수에 대해 3분이며, 모델 로딩과 warmup 시간은 포함하지 않는다.

2개 로봇의 최대 배치 순서는 반복별 1→2 / 2→1 / 1→2였다. 4개 로봇은 1→2→4 / 2→4→1 / 4→1→2로 순서를 바꿨다. 같은 seed를 반복해도 비동기 실행 시점까지 같아지는 것은 아니다. 세 번의 결과로 다른 task·seed·GPU에서도 같은 순위라고 일반화할 수는 없다.

step 간격 p95는 모든 조건에서 약 54ms였지만, action 부족 중에도 기본 action으로 환경 step이 진행한다. 따라서 step 처리량이 비슷하다는 이유로 모델 action 공급도 충분하다고 판단하면 안 된다. chunk 수신 간격은 각 로봇의 동일 에피소드 안에서 연속 수신 시각의 차이만 집계했다.

4개 로봇·최대 배치 1에서 chunk 수신 간격은 약 668ms로 늘어났다. 최대 10 step을 모두 사용할 수 있어도 20Hz에서 500ms 분량이므로, 공급 간격이 길어지는 현상은 높은 action 부족과 일관된다. 실제 사용 가능한 action 수는 응답 도착 시점과 실행 위치에도 영향을 받으므로 이것만으로 모든 부족 구간의 원인을 확정하지는 않는다.

chunk 지연은 관측 생성 이후 직렬화 직전의 request_timestamp부터 클라이언트 broker가 응답을 chunk로 만드는 response_timestamp까지다. 순수 네트워크 RTT나 관측 생성부터 action 실행까지의 전체 시간은 아니다. 서버는 최신 관측을 선택해 처리하므로, 처리된 관측의 응답 지연이 짧아도 로봇이 다음 chunk를 오래 기다릴 수 있다.

추론 worker 1개와 LIBERO EGL 렌더링 프로세스가 같은 GPU 0을 공유했다. 따라서 이 비교에는 렌더링과 CPU 시뮬레이션 부하가 포함된다. GPU 메모리는 약 5초 간격 샘플의 최댓값이며 정확한 peak가 아니다. 실행 중 다른 compute PID는 감시했지만, 이것이 공용 서버의 모든 CPU·그래픽 간섭을 배제한다는 뜻은 아니다.

Nsight Systems는 기존 설치본으로 수집했고 CPU sampling/context-switch 수집은 껐다. 실제 GPU worker에서 15.325초 구간, 일반 CUDA kernel 118,366개와 CUDA Graph 실행 60,738개를 확인했다. 완결된 추론 NVTX 87개를 batch ID로 서버 로그와 연결했으며 시작·종료 차이는 최대 0.028ms/0.015ms였다. 수집 경계에서 닫히지 않은 NVTX 범위는 duration 집계에서 제외했다. 이 수치는 GPU utilization이나 SM 활용률을 뜻하지 않는다.

이번 변경으로 선택 당시의 request ID와 실제 처리한 request ID를 함께 기록하고, chunk ID로 클라이언트·서버 로그를 연결했다. 저장된 일반 실행 chunk **20,000개**를 모두 실제 처리 ID 및 chunk ID와 일대일 대조했다. 클라이언트 오류 패턴은 없었고, 각 실행의 서버 연결과 자동 PNG 그래프 13개 생성을 확인했다. 종료 직전에 응답을 받지 못한 truncated 에피소드는 chunk 파일이 없는 정상 사례로 처리하되 해당 step과 초기 action 부족은 집계에 포함했다.

코드 검증에는 실제 처리 관측/기존 로그 형식의 timing join, server log 링크 경로 보호, Nsight 자식 프로세스 소유권, 재개 시 조건 일치, chunk 없는 짧은 종료 에피소드 회귀 검증 및 mock serving/scheduler/broker 검증을 사용했다. 수정 파일의 ruff와 git diff --check도 통과했다.
