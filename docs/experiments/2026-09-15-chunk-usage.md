여기서 별도로 발견한 문제가 에피소드 간 응답 유입이다. 서버 관측 step 0 경계로 원관측의 에피소드를 재구성하고, 원본 step 시각과 request_timestamp를 대조했다. 다음 229개는 모두 저장된 에피소드 바로 이전 에피소드의 관측을 사용했다. 해당 원본 step 기록 시각은 request_timestamp보다 18.8~33.7ms 뒤였고, 저장된 에피소드의 첫 step보다 관측 요청이 285~506ms 먼저 발생했다. 즉 에피소드 번호만의 우연한 불일치가 아니다.

229개 모두 실제로 사용됐고, 영향을 받은 다음 에피소드도 229개다. 예를 들어 run_r2_b1_rep1/robot_0의 에피소드 1에서 observation step 188을 사용한 응답이 에피소드 2에 저장되어 action 3개를 실행했다. broker.reset은 로컬 queue를 비우지만, 현재 InferRequest/InferResponse에는 에피소드 세대를 식별하는 필드가 없고 수신 경로도 현재 에피소드의 응답인지 검사하지 않는다. 따라서 초기화 뒤 늦게 도착한 이전 응답이 다시 queue에 들어갈 수 있다.

기존 실험의 성공·부족 수치는 이 동작을 포함한 관측 결과다. chunk의 request ID가 서버와 맞는다는 기존 검증은 에피소드의 일치까지 보장하지 않았다. 이 229개 행만 빼도 이미 그 action으로 바뀐 시뮬레이터 상태는 되돌아가지 않으므로, 행을 제외하는 분석으로 수정 후 재실행을 대신할 수 없다. 참고로 같은 에피소드에서 만들어진 chunk만 집계해도 4대·최대 배치 2/4의 실행 action 평균은 7.23/6.74개였지만, 이것도 수정된 동작의 반사실적 실험 결과는 아니다.

request_to_step_record_ms도 저장했다. 이는 직렬화 직전 request_timestamp부터 apply_action 뒤에 기록한 step 시각까지의 간격이다. 관측 생성 시간은 빠져 있고 action 실행 시작 시각과도 다르므로 완전한 sensor-to-action age로 부르지 않는다. 조건별 실행 p95의 평균은 2대 최대 배치 1/2가 약 489/491ms, 4대 1/2/4가 677/672/673ms였다. 이전 에피소드 응답도 포함한 원본 동작의 지표다.
